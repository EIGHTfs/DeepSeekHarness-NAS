# 反代媒体请求内部直通设计（2026-10-06）

> **状态**：设计稿，**尚未实施**（本文只记录方案，不改动任何脚本）。
> **实施位置**：`build/start.sh.example`（所有 start.sh 的母版，由 `pack-spk.sh` / `pack-fpk.sh` 经 `gen_start_sh` 依 `build-config.yaml` 生成）。

## 一、问题

当反代启用门户自动认证后，会出现一个只在**首次访问**暴露的现象：

- 视频类壁纸 / 开屏动画长时间黑屏，甚至一直不出画面；刷新或第二次打开就正常。
- 直接取同一个媒体文件很快（可达数百 MB/s），页面里却“加载不出来”。
- 打开 Network 面板可见媒体请求经历了一次 **302 重定向**。

## 二、根因

1. 反代的门户认证规则是「GET 且 URL 不带 `token=` 且没有 `dsh-auth` 会话 cookie」→ 302 到带 token 的同一地址（用于首次自动认证）。
2. `<video>` / `<audio>` 加载媒体时发送的是 **`Range` 请求**（分段拉流，响应 206）。
   浏览器**跟随 302 时会丢弃 `Range` 请求头**，重定向后的请求就变成**从头整文件下载**。
3. 结果是：几百 MB 的视频要**全部下载完**才有首帧 → 表现为「卡住 / 加载不出来 / 开屏黑屏很久」。
4. **为什么只有第一次**：首次访问会完成一次 token 认证并建立会话 cookie，此后请求都带 cookie、不再被重定向。
5. **为什么命令行测不出来**：`curl -L` 默认会**保留 Range 头**跟随重定向，因此测出来很快；只有浏览器媒体元素的行为会丢 Range。

补充事实（已实测）：**DSH 应用自身对媒体资源是放行的**——直接请求内部端口（`127.0.0.1:<dsh-port>`）的媒体 Range 请求返回 **206**。
因此媒体请求并不需要经过认证重定向，重定向只是反代在入口处统一加上的。

## 三、设计

思路：**媒体请求不参与认证 302，直接转发给 DSH 应用**（“内部直通”）。其余请求（导航、HTML、接口）认证行为完全不变。

### 3.1 新增媒体请求判定（`isMediaRequest`）

放在 `isDirectAccess` 定义之前，三重兜底判定：

```js
  // 媒体请求判定（video/audio/image 元素发起的资源请求，或带 Range 的分段请求）：
  // DSH 应用对媒体资源本身直接放行（206）；而媒体元素跟随 302 重定向会丢失 Range 语义，
  // 退化为整文件下载、首帧长时间卡住。故媒体请求一律内部直通，不做认证 302。
  const isMediaRequest = (req) => {
    const dest = req.headers['sec-fetch-dest'];
    if (dest === 'video' || dest === 'audio' || dest === 'image' || dest === 'track') return true;
    if (req.headers.range) return true;   // 带 Range 的分段请求（含 preload=metadata 探测）
    return /\.(mp4|webm|mkv|mov|mp3|ogg|m4a|wav|flac|png|jpe?g|gif|webp|avif|bmp|svg|ico)(\?|$)/i.test(req.url || '');
  };
```

### 3.2 两处放行条件

**① 门户打开 → 302** 的条件追加 `!isMediaRequest(clientReq)`：

```js
    if (dshToken && clientReq.method === 'GET' &&
        !clientReq.url.includes('token=') &&
        !hasAuth &&
        !isMediaRequest(clientReq) &&        // 新增：媒体请求内部直通
        !clientReq.headers.upgrade) {
      autoAuthRedirect(clientReq, clientRes);
      return;
    }
```

**② 401 兜底 → 302** 的条件追加同一项：

```js
      if (dshToken && proxyRes.statusCode === 401 && clientReq.method === 'GET' &&
          !clientReq.url.includes('token=') && !isMediaRequest(clientReq) &&   // 新增：同上
          !clientReq.headers.upgrade) {
        proxyRes.resume();
        autoAuthRedirect(clientReq, clientRes);
        return;
      }
```

### 3.3 不改动项

- **转发目标**：媒体请求落到既有转发逻辑（`hostname: '127.0.0.1', port: dshPort`），应用侧返回 206。
- **403 分支**（无 cookie 且判定为直连导航）：媒体请求不是文档级导航，不会命中该分支，无需改动。
- **媒体响应头策略**：`video/*`、`image/*` 保留后端缓存头（`public, max-age=86400` + ETag），其余 `no-store`——保持现状。

## 四、风险与准入口径

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| 未认证者可直取媒体文件 | 中 | 内网可达者免认证下载壁纸/音乐 | 仅“带 Range 或媒体扩展名”直通；如需更严可再限定来源为私网/loopback |
| 旧浏览器无 `sec-fetch-dest` | 中 | 判定失效 | `Range` 头 + 扩展名双重兜底 |
| 应用侧对媒体返回 401（个别部署） | 低 | 媒体不加载（但不会退化为整文件下载，也不会锁死） | 记录在案；必要时后续加“媒体 401 带 token 重转发” |
| 误判：带扩展名的非媒体被直通 | 低 | 绕过认证 | 扩展名白名单只含媒体/图片，排除 `.js/.json/.html` |

**边界条件**：

1. 无 `Range` 头的整文件媒体请求 → 仍直通（扩展名兜底）。
2. `HEAD` 探测请求 → 直通（只返回状态与头）。
3. URL 已带 `?token=` → 命中既有“已带 token 放行”，与本次判定无冲突。
4. WebSocket `upgrade` → 原条件保留，媒体判定不参与。
5. `sec-fetch-dest: empty`（fetch/XHR）但 URL 为媒体扩展名 → 由扩展名判定覆盖。
6. 并发大量 Range 请求 → 走同一转发路径，无新增资源竞争。

## 五、验证方案

**改前基准**：无 token、无 cookie 的 `curl -r 0-1023 http://<host>:<proxy-port>/<媒体路径>` → **302**。

**改后预期**：

| 用例 | 期望 |
|---|---|
| 无 token / 无 cookie 的媒体 Range 请求 | **206**（不再 302） |
| 无 cookie 的 `curl -I http://<host>:<proxy-port>/`（导航） | **仍 302**（认证不变） |
| 带 `?token=` / 持 `dsh-auth` cookie / 门户打开 | 行为不变 |
| `bash -n build/start.sh.example` | 语法通过 |
| `gen_start_sh` 产物 grep `isMediaRequest` | 命中 3 处（1 定义 + 2 条件） |

**人工验证**：浏览器无痕首次打开页面，Network 面板确认媒体请求无 302、首帧时间明显提前。

**回归**：门户打开 / 带 token 直访 / 持 cookie 直访三条既有路径行为不变。

## 六、生效路径

1. 修改母版 `build/start.sh.example`。
2. 重新打包（`pack-spk.sh` / `pack-fpk.sh`，或经 `gen_start_sh` 单独生成 start.sh），产物中出现新增判定与两处条件。
3. 部署新包并重启实例后生效——**运行中的实例不会因母版改动而变化**（母版改动本身不影响当前进程）。
