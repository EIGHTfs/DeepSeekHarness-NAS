# 群晖（DSM）下的资源限制

DSM 7 用 systemd 管第三方套件，unit 名为 `pkg-<包名>.service`。群晖的 systemd 与内核对 CPU/内存限制的支持与通用发行版不同，照搬通用写法会得到「命令成功但限制不生效」的伪成功。

改任何限制前，先 `cat /proc/<pid>/cgroup` 确认目标进程挂在哪个 unit，再对该 unit 下手。

## 1. CPU：用 taskset 绑核，CPUQuota 无效

`systemctl set-property pkg-<包名>.service CPUQuota=300%` 会返回成功、`systemctl show` 也显示已设置，但进程实际不限速：群晖的 cpu cgroup 只有 `cpu.shares`，没有 CFS 带宽文件可写，限制只是被接受。

改用 `taskset`（走 `sched_setaffinity`，内核必然支持）：

```bash
taskset -pc 0-2 <dsh_pid>          # 绑到 0-2 三核，给系统留余量
```

持久化就在启动命令前加前缀：

```sh
taskset -c 0-2 <node_bin> <dsh_entry> web --port <port> --no-open
```

验证：

```bash
cat /proc/<pid>/status | grep Cpus_allowed_list    # 期望 0-2
```

## 2. 内存：属性名是 MemoryLimit

群晖的 systemd 较老，`MemoryMax` 报 `Unknown assignment`，只有 `MemoryLimit` 生效。用 drop-in 持久化：

```ini
# /etc/systemd/system/pkg-<包名>.service.d/limits.conf
[Service]
MemoryLimit=10G
```

```bash
systemctl daemon-reload
```

验证（cgroup v1；v2 换成 `memory.max`）：

```bash
cat /sys/fs/cgroup/memory/system.slice/pkg-<包名>.service/memory.limit_in_bytes
```

## 3. 手动重启后进程落在根 cgroup

用启停脚本 `restart` 后，`taskset` 绑核仍生效，但 `/proc/<pid>/cgroup` 显示 `/`，内存限制覆盖不到。

原因：手动执行时进程继承调用者（SSH shell）的 cgroup；只有开机阶段由 systemd 跑 rc.d 时才会继承 unit 的 cgroup。对已 `active (exited)` 的 oneshot unit 执行 `systemctl start` 也不会重跑脚本。

做法：启动完成后把新 PID 写进目标 unit 的 tasks 文件（开机时已在其中，写入幂等）：

```sh
for controller in memory cpu cpuacct devices; do
  tasks_file="/sys/fs/cgroup/${controller}/system.slice/pkg-<包名>.service/tasks"
  [ -f "$tasks_file" ] && echo "$new_pid" > "$tasks_file" 2>/dev/null
done
```

验证必须在**重启之后**做，不能只测当前运行中的进程：

```bash
cat /proc/<new_pid>/cgroup
cat /sys/fs/cgroup/memory/system.slice/pkg-<包名>.service/memory.limit_in_bytes
```

## 4. 备选手段

- `nice -n 10 <cmd>`：只降调度权重，不做硬上限。
- `ulimit -v <KB>`：限虚拟内存；Node 预分配大，容易误伤。
- Node 堆上限由启动脚本的 `--max-old-space-size` 控制，属进程内约束，与 cgroup 是两套东西。
