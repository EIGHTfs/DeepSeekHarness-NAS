# 群晖（DSM）下的资源限制

DSM 7 把第三方套件统一交给 systemd 管（unit 名形如 `pkg-<包名>.service`，用 `systemctl list-units | grep -i <包名>` 实查确认）。给套件加 CPU / 内存限制时，群晖的内核与 systemd 版本和常见 Linux 发行版有差异，照搬通用做法会得到「命令成功但限制不生效」的伪成功。

以下三条均为 SA6400（DSM 7.x）实机实测，改动前先 `cat /proc/<pid>/cgroup` 确认目标进程挂在哪个 unit 下，再对该 unit 下手。

## 1. CPU：`CPUQuota` 在群晖无效，用 `taskset` 绑核

- 现象：`systemctl set-property pkg-<包名>.service CPUQuota=300%` 返回成功，`systemctl show` 也显示 `CPUQuota=3s`，但进程实际不限速。
- 根因：群晖内核的 cpu cgroup 只提供 `cpu.shares`，没有 `cpu.cfs_quota_us` / `cpu.cfs_period_us`（CFS 带宽）。限制没有可写入的真实文件，命令只是「被接受了」。
- 可行做法：`taskset`（走 `sched_setaffinity`，内核必支持）。

```bash
taskset -pc 0-2 <dsh_pid>          # 运行时：绑到 0-2 三核，系统留出余量
```

持久化就在启动命令前加前缀，例如自启脚本里：

```sh
taskset -c 0-2 <node_bin> <dsh_entry> web --port <port> --no-open
```

验证：

```bash
cat /proc/<pid>/status | grep Cpus_allowed_list    # 期望 0-2
```

## 2. 内存：属性名是 `MemoryLimit`，不是 `MemoryMax`

- 群晖的 systemd 版本较老，`MemoryMax` 会报 `Unknown assignment`；`MemoryLimit=10G` 才能落地。
- 持久化用 drop-in：

```ini
# /etc/systemd/system/pkg-<包名>.service.d/limits.conf
[Service]
MemoryLimit=10G
```

```bash
systemctl daemon-reload
```

验证（cgroup v1 路径；若为 cgroup v2 换成 `memory.max`）：

```bash
cat /sys/fs/cgroup/memory/system.slice/pkg-<包名>.service/memory.limit_in_bytes
```

## 3. 手动重启后进程落在根 cgroup，限制不生效

- 现象：用启停脚本 `restart` 后，新 PID 的 `taskset` 绑核仍生效，但 `/proc/<new_pid>/cgroup` 显示 `/` —— 内存限制没有覆盖它。
- 根因：手动执行脚本时，进程继承的是**调用者**（SSH shell）的 cgroup；只有开机阶段由 systemd 执行 rc.d 脚本时，进程才会继承 unit 的 cgroup。且对已 `active (exited)` 的 oneshot unit 执行 `systemctl start` 不会重跑脚本。
- 做法：启动完成后把新 PID 写进目标 unit 的 tasks 文件（开机时本就在其中，写入是幂等的）。

```sh
for controller in memory cpu cpuacct devices; do
  tasks_file="/sys/fs/cgroup/${controller}/system.slice/pkg-<包名>.service/tasks"
  [ -f "$tasks_file" ] && echo "$new_pid" > "$tasks_file" 2>/dev/null
done
```

验证（必须**重启之后**再测，不能只测当前运行中的进程）：

```bash
cat /proc/<new_pid>/cgroup                          # 期望落在 pkg-<包名>.service
cat /sys/fs/cgroup/memory/system.slice/pkg-<包名>.service/memory.limit_in_bytes
```

## 4. 备选手段

- `nice -n 10 <cmd>`：降 CPU 优先级（只影响调度权重，不做硬上限）。
- `ulimit -v <KB>`：限虚拟内存（对 Node 这类预分配较大的运行时容易误伤，慎用）。
- 应用层限制：本项目自身的 Node 堆上限由启动脚本的 `--max-old-space-size` 控制（见 `build/start.sh.example`），那是进程内的约束，和 cgroup 是两套东西。
