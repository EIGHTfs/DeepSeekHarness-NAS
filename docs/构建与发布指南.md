# 构建与发布指南

面向维护者：从官方源码到 `.spk` / `.fpk` 产物，以及 CI 自动构建与发布。包结构与不变量见 `打包规范.md`。

## 1. 构建链路总览

```
scripts/prepare-build-env.sh       构建环境准备（幂等、不 mount）
        ↓
scripts/fetch-dsh-latest.sh        拉官方源码 → src/deepseek-ai/<tag>
        ↓
build/build-common.sh              公共预编译：install → build → 裁剪 → target
        ↓
build/SPK/pack-spk.sh  build/FPK/pack-fpk.sh     消费 target 出包 → build/staging/
        ↓
scripts/promote-release.sh         验证通过的产物提升到 release/
        ↓
GitHub Actions                     发布 Release（含双产物 + sha256）
```

构建只做一次：`build-common.sh` 产出 target，两个打包器只消费不重编。

## 2. 本地构建

```bash
./build/build-common.sh [SRC] [SKIP_BUILD] [--dry-run] [--work-dir DIR]
```

| 写法 | 效果 |
|---|---|
| `./build/build-common.sh` | 全量：复制源码 → install → build → 裁剪 → 写 `build-meta.env` |
| `./build/build-common.sh "" 1` | 复用已有 target，秒级（快速重打包） |
| `./build/build-common.sh --dry-run` | 全阶段预演，只列计划不执行 |
| `./build/build-common.sh --work-dir /tmp/w` | 中间产物落到指定目录（缺省 `build/master-build`，行为不变） |

`SRC` 可空：留空按 semver 通配扫描 `src/deepseek-ai/*` 取最新，其次 `build/master-build/master-build`。`SKIP_BUILD` 传 `1` 复用 target，留空 = 全量。

`--work-dir DIR`（亦可 `D_WORK_ROOT` 环境变量）：把 `source/`、`target/`、`build-meta.env` 整体放到指定目录，适合
① 工作区在 CIFS/SMB 上（深层目录删除慢、`rm` 常报 `Directory not empty`）时把中间产物移到本地盘；
② 同时保留多份不同源码的构建产物（各用各的目录，互不覆盖）。打包脚本要读同一份产物时同样传 `--work-dir`：

```bash
./build/build-common.sh --work-dir /volume1/work/dsh-rc1 --src src/deepseek-ai/dsh-v0.2.2-rc.1 0
./build/SPK/pack-spk.sh --work-dir /volume1/work/dsh-rc1
./build/FPK/pack-fpk.sh --work-dir /volume1/work/dsh-rc1
```

打包：

```bash
./build/SPK/pack-spk.sh                 # → build/staging/DeepSeekHarness-NAS_x86_64-<版本>.spk
./build/FPK/pack-fpk.sh                 # → build/staging/DeepSeekHarness-NAS_x86-<版本>.fpk
./build/build-test-fpk.sh               # 测试版 FPK（含版本标记，调试用）
```

打包脚本默认无参数（端口/品牌/描述读 `build/build-config.yaml`）；要读别的构建目录时传 `--work-dir DIR`。

FPK npm 链路（可选，免源码编译，体积更小）：

```bash
./build/build-npm-app.sh [VERSION]      # npm 装官方包 → build/master-build/npm-app-<版本>/app_root
./build/FPK/pack-fpk.sh --npm           # 消费 app_root 出 fpk（产物后缀 -npm）
```

默认链路是源码构建（与 SPK 同源）；npm 链路保留为本地手动可选，CI 不执行。

## 3. 分阶段与环境变量

```bash
BUILD_STAGE=install ./build/build-common.sh     # 只做复制源码 + pnpm install
BUILD_STAGE=build   ./build/build-common.sh     # 只做 build
BUILD_STAGE=prune   ./build/build-common.sh     # 只对已有 target 重新裁剪 + 补包
```

| 变量 | 默认 | 含义 |
|---|---|---|
| `PRUNE_BEFORE_INSTALL` | `1` | install 前剥离非白名单 devDeps（省 install 峰值磁盘） |
| `PRUNE_BEFORE_BUILD` | `1` | install 后、build 前裁 `.pnpm`（省 build 内存/磁盘）；`0` 关闭 |
| `SKIP_BUILD` | `0` | `1` 复用已有完整 target |
| `BUILD_STAGE` | `all` | `install` / `build` / `prune` / `all` |
| `NPM_MODE` | `0` | `1` = FPK 走 npm 链路 |
| `DRY_RUN` | `0` | 只打印计划不执行 |
| `DSH_TSC_MEM` | 可用内存 75% | tsc 堆上限（MB） |
| `DSH_NODE_DIST` | 自探测 | node 发行版目录（`resolve_node()` 顺序：`/usr/bin/node` → `$DSH_NODE_DIST/node-v*/bin/node` → `tools/node-dist/`） |
| `DSH_GIT_BIN` | 自探测 | git 可执行路径（群晖 git 常不在 PATH） |
| `DSH_VERSION` | 空 | 指定拉取的官方源码版本 |
| `DS_FETCH_TOKEN` | 空 | 拉源码 token（等价 `--token`；不传匿名，限流 60 次/小时） |
| `DS_FETCH_GIT_URL` | 官方仓库 | git 远端覆盖（走镜像/内网） |
| `DSH_GIT_MIRROR_PREFIX` | 空 | GitHub 镜像前缀（如 `https://gh-proxy.com/`），把 git 协议的 `https://github.com/` 改写走镜像 |
| `ARCH` / `BUILD_ARCH` | `x86_64` | 目标架构覆盖 |
| `APP_NAME` `D_SRC` `D_BUILD` `D_STAGING` `D_REL` `D_SCRIPTS` `D_ASSETS` | 读 config | 名称与分类目录临时覆盖 |

工作区目录三级优先级：**命令行参数 > 环境变量 > `build/build-config.yaml` 的 `defaults.*_dir` > 默认值**。脚本启动自检分类目录并创建输出目录，路径写错立即报错。

本地构建必须在**可执行挂载**上跑：群晖上 `@appdata/.../工作区` 可执行，`VirtualDSM/...` 这类挂载是 noexec，构建会失败。

## 4. 裁剪与白名单

裁剪是**纯白名单**语义：不在白名单里的 `.pnpm` 目录一律删除。白名单三层合成：

| 层 | 来源 | 维护方 |
|---|---|---|
| `lockfileDeps` | `build/gen-prune-whitelist.sh` 从 npm 链路 `package-lock.json` 的 packages 键解析 | 脚本生成 |
| `workspaceRuntimeDeps` | 打包期动态扫描 `target/packages/**/package.json` 的 `dependencies` | 自动收集 |
| `extra` + `_autoLearned` | 手工补充项 + `scripts/learn-prune-whitelist.sh` 学习结果 | 手工 + 自动 |

口径：`extra` 只在 install 前模式用于保护 tsc，不进最终 target；出货裁剪（模式 B）的白名单是 `lockfileDeps` + `workspaceRuntimeDeps` + `_autoLearned`。`gen-prune-whitelist.sh` 只写 `lockfileDeps` 键，不覆盖 `extra` 人工项。

```bash
./build/gen-prune-whitelist.sh [锁文件] [--dry-run]      # 留空自动找最新锁文件
./build/prune-target.sh --before-install <SRC>           # install 前剥非白名单 devDeps
./build/prune-target.sh --node-modules <SRC>             # install 后、build 前裁 .pnpm
./build/prune-target.sh <TARGET> [WHITELIST]             # 裁已构建 target
scripts/learn-prune-whitelist.sh                         # 静态扫描学习
scripts/learn-prune-whitelist.sh --log <FILE>            # 从失败日志反查学习
```

学习器两种模式能力不同：

| 模式 | 输入 | 覆盖 | 盲区 |
|---|---|---|---|
| `--scan <SRC>` | 官方源码 | `package.json` scripts 引用的入口脚本（含相对 import 递归）∩ 将被剥离的根 devDeps | 官方新增的「非入口构建期脚本」扫不到 |
| `--log <FILE>` | 构建/安装日志 | `Cannot find module/package 'X'`；`Could not find a declaration file for module 'X'` → `@types/X` | 依赖日志本身能反映问题 |

CI 用的是 `--log`。

裁剪范围（有依据，非盲删）：非 linux-x64 平台变体、devDependencies 及其传递依赖、claude-agent-sdk / codex、`packages|apps` 的 src 与 docs/benchmarks。保留：`bin/node` + `bin/dsh` + `bin/pnpm` + 随包 pnpm + 各包 lib/dist + 运行时 node_modules + 原生模块（node-pty / sharp / koffi / esbuild / ripgrep）。

平台裁剪：pnpm 会拉所有平台的原生二进制变体（约 1.4GB），预编译阶段只留 `linux-x64-gnu` / `linux-x64-musl`。

体积门禁：`defaults.size_limit_mb`（当前 200），超限报错退出。

## 5. 依赖补齐与链接修复

```bash
build/fix-runtime-deps.sh <TARGET> <BUILD_SRC> <NODE> [--max-rounds N]   # 探测内置插件入口 import，补缺失闭包
python3 build/fix-node-links.py <应用体或 target> [--quiet]                # 三层链接补全 + 错链纠正（幂等）
scripts/fix-pnpm-store.sh <目标树>                                          # 修 .modules.yaml 的 storeDir 记录
```

要点：

- **运行时补包必须在 `build-common.sh` 里**（裁剪之后、写 meta 之前）。CI 的打包 job 只有 target artifact，没有构建副本 `BUILD_SRC`，放在打包脚本里会被静默跳过。
- **补包不只补缺、还要纠正已存在的错链**；pnpm 链接分三层（顶层 `node_modules/<包>`、提升 `.pnpm/node_modules/<包>`、包内 `.pnpm/<包>@<ver>/node_modules/<依赖>`），Node 从入口向上查找命中的是顶层，三层都要建。
- **包内/提升层的版本要按消费者声明的 semver 范围选**，多版本一律取最高会让包拿到不兼容版本（表现为 `Named export 'x' not found` 或 `invalid media type` 一类运行期异常）。构建期 `fix-node-links.py` 与运行期 `start.sh` 自愈用同一口径。
- 实机缺包兜底：`./start.sh fix-deps`（读启动日志 `Cannot find package 'X'` → 用随包 pnpm 补 → 重试一次启动）。刻意不做全量悬空链扫描补齐：绝大多数悬空链是构建期 devDependencies，全补等于把裁掉的依赖装回来。

## 6. 架构参数化

```yaml
# build/build-config.yaml
defaults:
  arch: x86_64        # x86_64（默认）| arm64；别名 x64/amd64、aarch64/armv8
```

| 取值 | SPK `arch=` | SPK 产物名 | FPK `platform=` | FPK 产物名 |
|---|---|---|---|---|
| `x86_64` | `x86_64` | `..._x86_64-<ver>.spk` | `x86` | `..._x86-<ver>.fpk` |
| `arm64` | `armv8` | `..._armv8-<ver>.spk` | `arm` | `..._arm-<ver>.fpk` |

覆盖优先级：环境变量 `ARCH` / `BUILD_ARCH` > `build-config.yaml` > 默认 `x86_64`；解析收口在 `build/build-lib.sh` 的 `resolve_arch()`，脚本内不写死架构。

原生模块（sharp / node-pty / koffi / node-addon-*）由 `pnpm install` 按宿主架构选择，**必须在目标架构机器上构建**，交叉构建不可靠。CI 的 ARM 跑在 `ubuntu-24.04-arm` runner。

## 7. npm 源选择

装依赖前并发探测候选源，每个一次请求、超时 4 秒，取【HTTP 2xx/3xx 且**耗时最短**】者，再拿它跑 `pnpm install`；全不可达则回落默认源。规则是「最快者胜」而非「先回者胜」：只返回 200 但耗时接近超时的源属于假可用。加镜像只需往 `NPM_REGISTRY_CANDIDATES` 数组加一行。

两条配套：

- 参数类错误（`Unknown option` / `ERR_PNPM_BAD_OPTION` / `ERR_PNPM_INVALID`）不重试，立即中止。
- 所选源仍失败时，保留一次 npmmirror 兜底。

## 8. 拉取官方源码

```bash
./scripts/fetch-dsh-latest.sh [--token <ghp>]      # → src/deepseek-ai/<tag>，自动识别最新 tag
./scripts/fetch-dsh-latest.sh --print-tag          # 只输出 tag
```

token 只接受显式传入（`--token` 或 `DS_FETCH_TOKEN`），脚本不自找凭据文件；不传则匿名拉取。优先用本地 git 镜像增量拉取，退化到 clone / zipball。

下载本仓 Release 资产：

```bash
./scripts/fetch-release-mt.sh [--tag <tag>] [--only spk|fpk] [--threads N]
```

走 `api.github.com` 通道（不依赖 github.com 直连），aria2c 分段并发，失败回退单流；大小校验 + 已存在跳过；凭据取插件托管的 githubToken，不落命令行。

## 9. 内置 pnpm 与垫片

构建与随包分发一律用项目自带 pnpm（`tools/pnpm/`，`build-common.sh` 的 `PNPM_BIN` 固定指向它并前置 PATH），不用系统 pnpm。选 pnpm 11 是因为 10 在大型 workspace 上有 OOM。

pnpm 11 起不再读 `package.json` 的 `pnpm` 字段，`onlyBuiltDependencies` / `overrides` 只从 `pnpm-workspace.yaml` 读。由 `tools/pnpm-bridge.py` 幂等把 `package.json` 的 `pnpm.*` 转换合并进 `pnpm-workspace.yaml`（`onlyBuiltDependencies` → `allowBuilds`，其余同名透传，保留已有内容）。

`build-common.sh` 在 install/build 前自动生成 `tools/pnpm/bin/pnpm` 包装垫片（755，含 `shim v2` 标记防重复；内含本机绝对路径，故被 .gitignore 忽略）。垫片做三件事：

1. 带 `--pm-on-fail=ignore` 调用，锁死自带版本 —— pnpm 11 默认会读 `packageManager` 字段联网下载并切换版本，导致实际运行的不是随包验证过的那份。
2. 每次调用前幂等执行 `tools/pnpm-bridge.py --dir "$PWD"`。
3. `exec "$NODE_SRC" "$PNPM_BIN"`，用打包用 node 跑自带 pnpm。

install 与 build 两处都走垫片，并前置 `PATH="$PNPM_BIN_DIR:$PATH"`，使上游 `sh -c` 起的子进程同样命中垫片（上游构建脚本会重新查 PATH，缺垫片时在无系统 pnpm 的环境报 `pnpm: not found`）。

## 10. native 构建自探测

官方 `build:native-system` 用 `cc` 编译 Node-API 附件，依赖 C 编译器与 node 发行版头文件（`include/node/node_api.h`，套件裁剪版 node 没有）。`build-common.sh` 全自探测，无需手动传参：

1. **NODE_SRC**：`tools/node-dist/node-v*/bin/node`（含 headers）→ PATH 中带 headers 的 node → 兜底 `/usr/bin/node`；探测到的 node 目录自动注入 PATH；显式 `NODE_SRC=` 仍最高优先（CI 走 setup-node 路径）。
2. **无 C 编译器**时自动启用「cc 替身 + 官方预编译产物」完成 `build:native-system`，官方 build 链其余步骤照跑。复用依据是官方 native 产物的确定性（不同来源的 `system.node` md5 一致）。有编译器时仍走真实编译。
3. 预编译产物查找顺序：本机构建副本 → 已装套件 `native/system/…` → `master-build` 缓存内的官方 npm 包。

## 11. GitHub Actions

| workflow | 作用 |
|---|---|
| `.github/workflows/build.yml` | 主构建。job：`build-target`（setup → fetch → 守卫 → `build-common.sh` → 上传 target）+ `pack-and-release`（复用 target → 打 SPK + FPK → 发 Release） |
| `.github/workflows/watch-official.yml` | 官方更新看门狗 |

触发方式：看门狗自动对齐（主通道）、Actions 页手动 `workflow_dispatch`（入参 `arch` = `x86_64`/`arm64`、`dsh_tag` 指定官方 tag）、推送 tag。

**看门狗**：cron 写的是每 30 分钟比对官方最新 tag 与本仓最新 Release tag，三条件全满足才触发构建 —— ①尚未对齐；②当前无构建在跑（`build.yml` 是 `cancel-in-progress: true`，插队会取消正在跑的）；③距最近一次成功构建 ≥ 6 小时。判定无状态，不依赖额外存储。权限 `contents: read` + `actions: write`，自身不并发、不取消别人。每日定时构建已取消（cron 是无条件构建，会废掉「成功后暂停 6 小时」这条）。

**实际触发频率远低于 30 分钟**：GitHub 对 `schedule` 事件有降频与限流（仓库不活跃时尤其明显），cron 表达式只是「期望值」。实测运行间隔约 8 小时（`#164` → `#165` → `#166` 分别间隔约 8.5 / 8 小时），不是配置写错。因此**官方发版到本仓出包可能延迟数小时**：`dsh-v0.2.2-rc.2` 官方发布于 11-11 11:33，本仓构建到 16:28 才被派发。需要立刻对齐时不要等 cron，直接在 Actions 页手动 `workflow_dispatch` 触发 `watch-official`（或直接派发 `build.yml` 并指定 `arch`）。

每次派发会**同时构建 x86_64 与 arm64**（两个 run 相隔约 1 分钟，属设计：只派发默认架构会导致 Release 里长期缺 ARM 包）。

**失败自愈**：`build-target` 失败时先跑「自动学习缺失依赖并入库」（从 `build/master-build/*.log` 与 `assets/pnpm-install.log` 反查缺失包 → 写白名单 → commit → push），仅当白名单确实改了才「自动重建一次」。安全边界：白名单无变化绝不提交，非缺包类失败不触发重建（无死循环）；缺包类失败每轮至少并入 1 个包，有限次收敛。两个实现要点：`changed` 输出必须写在 `push` 之前（push 被拒会让该步判失败、输出丢失）；重建步条件用 `always()` 而非 `failure()`。

**并发控制**：`concurrency: group=<workflow>-<ref>` + `cancel-in-progress: true`，同一时刻只有一个构建。

**缓存三层**：

| 缓存 | 键 | 换 tag 后 |
|---|---|---|
| 源码 git 镜像 `src/deepseek-ai/.cache` | `dsh-src-mirror-<repo>-<hash(build-config.yaml)>` | 命中，只拉增量 |
| pnpm store `assets/pnpm-store` | `pnpm-store-<os>-<hash(pnpm-lock.yaml)>` | 命中 |
| target | `dsh-target-v2-<tag>-<hash(构建脚本)>` | 必然未命中 → 完整构建 |

target 键必须含官方 tag：它是源码编译产物，换 tag 复用旧 target 会产出「版本号是新的、代码是旧的」的包。

**target 复用判据**：`build-common.sh` 认 `[ -f "$WORK/.build-done" ] && [ -d "$TARGET" ] && [ -f "$TARGET/package.json" ]`，缓存 tar 漏 `.build-done` 会让复用静默失效（解包后判据不成立 → 完整重编）。

**产物用 tar 单文件上传**：`upload-artifact` 逐文件处理海量文件会爆堆，先 `tar -czf` 再上传单个 `.tar.gz`（`compression-level: 0`）。

**产物开关与发布**：

| 仓库变量 | 默认 | 含义 |
|---|---|---|
| `vars.BUILD_SPK` / `vars.BUILD_FPK` | 空（都构建） | `false` 跳过对应产物 |
| `vars.PRUNE_OLD_ASSETS` | 空（启用） | `false` 关闭改名残留清理 |

Release tag 取官方最新 dsh tag（形如 `dsh-v<版本>`）；同名 Release 已存在则覆盖资产与正文（滚动刷新）；统一发正式 Release，不标 prerelease。构建失败即不打包、不发布。正文含每个产物的 sha256 与官方同 tag 更新日志（由 `build/release-note.sh` 渲染）。

**改名残留清理**：`action-gh-release` 只替换同名资产，产物一旦改名，旧名会一直挂在 Release 上让下载者选错。

```bash
python3 scripts/prune-release-assets.py --tag <tag> --keep-from <产物目录> [--dry-run]
```

安全规则：只处理本包前缀、只清理本次确实产出过的类别（架构 + 后缀 + 链路），未产出的类别一律不碰（故 `BUILD_FPK=false` 时不会误删上一轮 FPK）。

**install 前裁剪入 CI**：官方 monorepo 依赖树约 1.78 万包，install 会拉满 runner 磁盘，故先跑 `prune-target.sh --before-install`。注意被剥掉的根 devDep 若是某个构建期解析入口的唯一来源，其传递依赖会随之不安装，表现为 `TS2307`（例如剥掉 vitest → vite 缺失）。学习器解析 pnpm 安装摘要（`+ <包> <版本>`）自动补齐这类根 devDep。

### 缓存分层与重建成本

一次构建分三段，成本与输入各不相同：

| 段 | 做什么 | 耗时 | 真正依赖 |
|---|---|---|---|
| A 构建 | 复制源码 → install → build | ~15 分钟 | 官方 tag + 工具链 |
| B 裁剪 | `prune-target.sh` + 补包 | ~1 分钟 | 白名单 + 裁剪脚本 |
| C 打包 | 后处理 + 出 spk/fpk + 发布 | ~2 分钟 | 打包脚本 + `build-config.yaml` |

当前 target 缓存键把 B/C 的输入（白名单、裁剪脚本、打包 action）也算了进去，这些一改，所有历史 tag 的 target 全部失效；而最贵的 A 段其实与 B/C 无关。收敛方向两条：

1. **缓存内容从「已裁剪」改成「未裁剪」**：裁剪依赖白名单，缓存已裁剪产物就必然要把白名单塞进键；缓存未裁剪的 `source/`（含完整 node_modules，体积约 6.6G）后这个耦合消失。代价是体积，换来「白名单随便改都不用重建」。
2. **拆脚本以切分缓存键**：把 `build-common.sh` 的 A 段抽成独立脚本，L1 键只哈希 A 段输入；B/C 每次跑（约 3 分钟）。

另外 GitHub Actions 缓存 7 天未访问即回收，历史 tag 放久了会没 —— 长期基线要另存（本机缓存目录，`tar --zstd` 回写，CI 未命中 Actions 缓存时先查它）。

**只验证不打包**：验证一个打包/裁剪改动不需要出正式包，也不需要重跑 A 段：

```bash
BUILD_STAGE=prune ./build/build-common.sh          # 对已有 target 重新裁剪 + 补包
python3 scripts/check-packaging-invariants.py      # 打包不变量
python3 scripts/check-package-parity.py <基准包> <候选包>
```

判定口径（不产出安装包也能定论）：target 内 `.pnpm` 目录数不少于基准包、`links.tar` 每个目标在 target 内存在（复用 parity 工具的悬空检测，把载荷条目集换成 target 文件集）、不变量全绿。

## 12. 守卫与回归测试

改完必须全绿，任一失败即阻断提交：

```bash
python3 scripts/check-workflow-yaml.py          # YAML 结构、步骤缩进、needs 引用悬空
python3 scripts/check-readme-coverage.py        # 代码里的脚本名/开关名必须在 README 出现
python3 scripts/check-common-functions.py       # 公共函数不得在其它脚本重复定义
python3 scripts/check-destructive-ops.py        # 敏感路径 rm -rf 必须 --one-file-system
python3 scripts/check-build-naming.py           # 命名规范 + 全部 .sh/.py 语法 + 可执行位
python3 scripts/check-build-config.py           # defaults/spk/fpk 三段必须是映射
python3 scripts/check-packaging-invariants.py   # 打包不变量
bash test/learner-dryrun.test.sh                # 白名单学习器 dry-run 回归
bash test/prune-release-assets.test.sh          # Release 资产清理回归
```

守卫自身的纪律：

- **反向验证**：新增或修改守卫后，故意破坏对应代码 → 守卫必须退出码非 0；还原 → 必须为 0。替换词必须与原名无包含关系（只加后缀不算破坏，被检查的子串还在，得到的绿是假绿）。
- **内容检查先剥注释**：「文件中必须存在 X」的检查要先剔除注释行，否则命令原文写进注释就会假通过。
- **新检查器先在合格对照物上跑出 0 告警**：对照物报警 → 先修检查器，不得据此下「包有问题」的结论。
- **断言前先枚举真实写法**：计数/匹配类断言要覆盖同语义的所有写法（如 `<details>` 与 `<details open>`），最好再用解析器复核；文档里举例写的标签会被朴素计数器误当真实标签，需行首锚定并排除代码片段。
- **语法检查 ≠ 完整性检查**：`bash -n` / AST / `py_compile` 全过也可能少了整段内容，破坏性编辑必须 `assert 命中次数 == 期望值` + diff 复核 + 关键内容抽查。

## 13. 本地等效 CI

按第 2、3 节逐脚本跑，与 CI 共用同一套构建脚本；差别只在运行环境与编排。两条链路都必须遵守同一套守卫与 `scripts/lib/common.sh`，任何「只在本地能过」的环境变量覆盖都说明根因未修，应修进脚本而不是绕过。
