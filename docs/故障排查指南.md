# 故障排查指南

按「症状 → 快速判据 → 处置」组织。判据都是可直接复制的命令；`<app>` 为套件名 `DeepSeekHarness-NAS`，`<NAS-IP>` 用 `hostname -I` 取主网卡局域网地址。

## 0. 三分钟定位骨架

```bash
# ① 服务在不在跑（0=运行，3=未运行）
/var/packages/DeepSeekHarness-NAS/target/bin/start.sh status        # 群晖
/var/apps/DeepSeekHarness-NAS/cmd/main status                        # 飞牛（带 TRIM_* 环境，见 §1）

# ② 端口在不在听（期望 3 个：反代 / dsh / 容器页）
ss -ltn | grep -cE ':3080|:3081|:3082'                # 飞牛段
ss -ltn | grep -cE ':30800|:30801|:30802'             # 群晖段

# ③ 应用自身是否正常（绕过反代，直连 dsh 原生端口）
curl -s -o /dev/null -w '%{http_code}\n' http://<NAS-IP>:30802       # 容器页同策略入口

# ④ 平台自己的判定日志（飞牛）
grep -a "start app error" /var/log/trim_app_center/error.log | tail -5
```

分流：

| 观察结果 | 往哪节走 |
|---|---|
| status 非 0，或端口数不足 | §1 起不来 / 平台判启动失败 |
| 端口齐、`ss` 有监听，浏览器打不开 | §2 访问与入口 |
| 打开后白屏 / 每个请求都 400 | §3 页面异常 |
| 日志里 `failed to import` / `Cannot find package` | §4 依赖与链接 |
| 安装/卸载动作本身失败 | §5 安装错误码 |
| 构建（打包链路）失败 | §6 构建与 CI |
| 终端/命令行类异常 | §7 运行环境 |

## 1. 服务起不来 / 平台判启动失败

### 1.1 飞牛：应用其实在跑，但「打开」按钮不出现

**判据**

```bash
grep -a "start app error" /var/log/trim_app_center/error.log | tail -3    # 出现 error="10330:" 即命中
ps -ef | grep -c '[d]sh web'                                              # >0 说明应用是活的
ss -ltn | grep -cE ':3080|:3081|:3082'                                    # 3 说明端口也在听
```

三端口在听 + 应用中心报 10330 ⇒ 问题在**平台的启动判定**，不是应用没起来。

**再看生成物自判**

```bash
TRIM_APPDEST=/vol2/@appcenter/<app> TRIM_PKGVAR=/vol2/@appdata/<app>/<版本> \
  /var/apps/<app>/cmd/main status ; echo "rc=$?"
```

| 输出 | 根因 | 处置 |
|---|---|---|
| `running_dsh: 未找到命令`，rc=3 | 生成物调用了未定义的函数（实现只在 `scripts/lib/common.sh`，生成物不 source 它） | 按 `打包规范.md` §6 把函数实现写进生成物；跑 §6 的静态体检脚本确认「未定义调用」为空 |
| 无报错但 status 恒失败 | 生成物用了只在打包脚本赋值的端口变量，运行时为空 | 端口改用 `${DSH_PORT:-$FPK_DSH_PORT}` 这类运行时来源 |
| rc=0 且「✓ 服务运行中」 | 判定没问题，看下一节 | → §2 |

**注意**：`appcenter-cli check` 显示 Installed / list 的状态只代表平台「认为」的状态，真实情况用 `ss -ltnp` + `ps` 交叉验证。

### 1.2 群晖：synopkg 起不来

```bash
synopkg status <app>                                        # stopped / start_failed
synopkg start <app>
tail -50 /var/log/synopkg.log
```

| 现象 | 判据 | 处置 |
|---|---|---|
| 起不来后端口数为 0 | 看 `<数据目录>/<版本>/ports` 记录的端口是否被别的进程占用 | `ss -ltnp \| grep :<端口>` 找占用方；或改端口重启 |
| `start app error` 类 | dsh 自身启动异常 | → §4（缺包/链接）；必要时启用安全模式禁用所有用户插件 |
| 反复 restart 无效 | 插件加载异常 | `scripts/fix-dsh-settings-namespace.sh`（幂等、带备份）后重启 |

### 1.3 手动启动与套件启动打到不同实例

判据：`start.sh status` 报未运行，但 `ps -ef \| grep dsh` 有进程（或反之）。

原因：`DSH_HOME` 指向不同目录（SSH 里以 root 起会落到 `<HOME>/.dsh`，与套件实际使用的 home 不是一个位置）。

处置：统一走套件路径，或用 `start.sh` 自己探测（无 `TRIM_PKGVAR` / `SYNOPKG_PKGVAR` 注入时自动探测 `/var/packages/<app>/var` → `/volume*/@appdata/<app>`，解析到与服务侧同一个 DSH_HOME 与 PID 文件）。插件装在错误 home 的表现就是「装完不生效」，用 `dsh plugin --profile web list` 确认列出的就是服务在读的那份。

## 2. 访问与入口

### 2.1 打开就是 403「请从套件图标打开」

```bash
# 模拟「从图标打开」（不带 token、不带 cookie）
curl -sI -H "Sec-Fetch-Site: none" -H "Sec-Fetch-Dest: document" -H "Accept: text/html" \
     http://<NAS-IP>:3080/          # 期望 302 且 Location 带 token；403 = 异常
```

| 判定 | 处置 |
|---|---|
| 返回 403 | 反代的「自动带 token」分支排到了 403 之后，或 token 读不到 → 见 `打包规范.md` §9；跑 `./start.sh gen-portal --token` 重写门户 |
| 302 但 `Location` 里的 token 是旧的 | 陈旧 token：升级到含 token 兜底的版本（非当次 token 会自动 302 换成当次） |
| 想临时救急（旧版本） | 先用**容器页端口**（`http://<NAS-IP>:3082`）打开一次，再回反代端口——容器页走另一条同策略入口，会让 dsh 刷新 token，之后反代端口恢复；两端口同策略，不降低安全性 |
| 只有公网访问被 403 | 这是预期行为：局域网硬闸先于认证，公网来源一律拒 |

⚠ 用 curl 跟随时必须带 cookie jar（`-c j -b j`），否则看到 302/303 自循环——那是 curl 不存 cookie，不是服务问题。

### 2.2 浏览器 ERR_TOO_MANY_REDIRECTS

跨 scheme（DSM https:5001 → 套件 http:30800）时 `SameSite=Strict` 的 cookie 会被浏览器丢弃 → 无限 302。反代已把 dsh 响应的 `Strict` 改写为 `Lax`；仍出现即不是最新构建，换最新包。

### 2.3 桌面图标点不开 / 无「打开」按钮（群晖）

```bash
grep -o 'dsmappname=.*' /var/packages/<app>/target/INFO
python3 -c "import json;print(json.load(open('/var/packages/<app>/target/ui/config'))['.url'])"
```

两处 `SYNO.SDS.*` 键名必须**逐字一致**（`INFO` 侧去连字符）。不一致 → 图标点不开。端口由 DSM 自动拼真实地址，`ui/config` 里不应写死 url/IP。

### 2.4 反代端口不通但应用正常

```bash
ss -ltnp | grep -E ':(30800|3080)\b'      # 反代是否在听
tail -30 <数据父目录>/dsh-proxy.log        # 逐条 REQ/RESP/DENY，含 cookie 前缀
```

日志里 `DENY` 表示被局域网硬闸或入口收敛拦下；完全没有该请求记录表示请求没到反代（检查 IP/端口、以及是否用了 `<NAS-IP>` 而不是回环地址）。

## 3. 页面异常

### 3.1 页面每个请求都 400、空 body（应用看着在跑）

判据：

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://<NAS-IP>:30801/       # 直连 dsh 原生端口也 400 ⇒ 与反代无关
```

存在的文件全 400、不存在的路径给 404、`HEAD` 给 401、`POST` 给 405 ⇒ 是处理器抛异常被统一转成 400。

定位：

```bash
tail -60 <数据父目录>/dsh-proxy.log
ls <数据目录>/<版本>/.dsh/logs 2>/dev/null && tail -60 <数据目录>/<版本>/.dsh/logs/*.log 2>/dev/null
```

拿到形如 `TypeError: invalid media type`（栈里出现 `negotiator` / `compression`）⇒ **依赖链接层指错版本**：某包声明的范围与它实际解析到的版本不符。

处置：

```bash
python3 build/fix-node-links.py <应用体目录>        # 三层链接补齐 + 按声明范围纠正错链（幂等）
appcenter-cli stop <app> && appcenter-cli start <app>
```

修完应能看到大量「纠正」记录，随后连续几轮请求都 200。若反复复发，说明出货包里的链接层本来就是错的 → 按 `构建与发布指南.md` §5 重新打包。

### 3.2 视频/图片类资源首帧长时间不出（刷新或第二次打开正常）

判据：

```bash
grep -E "GET /(.*\.(mp4|webm|png|jpg))" <数据父目录>/dsh-proxy.log | tail -20   # 看媒体请求是否伴随 302
curl -sr 0-1023 -o /dev/null -w '%{http_code} %{size_download}\n' http://<NAS-IP>:3080/<媒体路径>   # 302 = 命中本节
```

机制：媒体元素发的是 `Range` 请求（响应 206），浏览器**跟随 302 时会丢弃 `Range` 头**，重定向后就变成整文件下载，几百 MB 的视频要下完才出首帧；首次访问完成 token 认证并种 cookie 后不再被重定向，所以只有第一次卡。命令行测不出来是因为 `curl -L` 会保留 `Range` 头。

处置：让媒体请求不参与认证 302、直接转发给 dsh 原生端口（应用侧对媒体本就返回 206）。判定条件三条任一：`Sec-Fetch-Dest` 为 `video`/`audio`/`image`/`track`；带 `Range` 头；URL 命中媒体/图片扩展名（`.js/.json/.html` 不在内）。改动落在母版 `build/start.sh.example` 的反代段（门户 302 与 401 兜底两处条件都要加），改完重新打包并部署新包才生效——母版改动不影响正在跑的实例。

### 3.3 改前端后整页按钮失效、页面看着正常

本仓已不含 HTML 页面（网页安装工具已独立为 `nas-pkg-installer` 仓库）。该仓库里的页面若出现
「按钮全失效但页面照常 200」，判据是内联脚本语法错误——用该仓库的
`scripts/check-html-inline-js.py` 以 `node --check` 真解析确认。

### 3.4 点「登录」弹窗一闪而过、提示操作未完成

浏览器登录只接受回环来源。判据：地址栏是 `http://<NAS-IP>:<反代端口>`（非 127.0.0.1 / localhost）时必然失败；换成回环地址后若恢复正常，即为此限制。

处置：用 `scripts/connect-local.sh <NAS-IP>` 建 SSH 本地转发（Windows 双击 `scripts/connect-local.bat`），在 `http://127.0.0.1:<端口>` 里登录；或改用 API Key（设置 → 账号 → 添加 API Key）。端口由脚本从目标机读取，本机端口被占用时用 `LOCAL_PORT=<端口>` 覆盖。

## 4. 依赖与链接

### 4.1 日志里 `failed to import` / `Cannot find package`

```bash
grep -c "failed to import" <数据父目录>/dsh.log 2>/dev/null
grep -o "Cannot find package '[^']*'" <数据父目录>/dsh.log | sort -u
```

| 场景 | 处置 |
|---|---|
| 实机运行中缺包 | `./start.sh fix-deps`（读日志缺包记录，用随包 pnpm 解析闭包补齐后重试一次启动） |
| 打包产物缺包 | 在 `build/build-common.sh`（裁剪之后、写 meta 之前）跑 `build/fix-runtime-deps.sh <TARGET> <BUILD_SRC> <NODE>`；不要在两个打包脚本里单独加（CI 无 `BUILD_SRC` 会静默跳过） |
| 构建期 `error TS2307` / `TS7016` | 白名单缺构建期依赖（`.pnpm` 实体还在，被删的是顶层解析入口）→ `scripts/learn-prune-whitelist.sh --log <失败日志>` 学进白名单；不要用 `PRUNE_BEFORE_BUILD=0` 长期绕过 |
| 学习成果没生效 | 确认出货裁剪（模式 B）的白名单并入了 `_autoLearned`（`python3 scripts/check-packaging-invariants.py` 会查） |
| 缺包但软链看着都在 | 三层链接缺顶层：`python3 build/fix-node-links.py <应用体>`；Node 从入口向上找，命中的正是顶层 |

### 4.2 `Named export 'x' not found` / 包被解析成 CJS 旧版

错链而非缺链：`.pnpm` 提升层把依赖指到了旧大版本。用 `fix-node-links.py`（会纠正错链，不只补缺）或 `start.sh` 的启动期自愈；根因口径见 `构建与发布指南.md` §5。

### 4.3 pnpm 报只读分区（EROFS）

```bash
pnpm config get storeDir ; df -h | grep -iE 'ro,|read'
```

`storeDir` 落在只读分区时：`pnpm install --store-dir=<可写路径>`；`pnpm run build` 用 `HOME=<可写临时目录>` 绕过全局配置。`build-common.sh` 已自动处理（走 `assets/pnpm-store` + `assets/tmp-home`）。另有 `scripts/fix-pnpm-store.sh <目标树>` 修 `.modules.yaml` 记录，无需重装。

## 6. 构建与 CI

| 症状 | 判据 | 处置 |
|---|---|---|
| 构建 0 秒失败，`Failed to load ./.github/actions/.../action.yml` | 步骤缩进与同级不一致 | `python3 scripts/check-workflow-yaml.py`（含 `check_step_indent`）；把新步骤缩进对齐同级 |
| 状态误判、Release 正文写成「缺失」 | `needs` 引用的 job 名不存在 | 同上守卫会直接拦 `needs` 悬空 |
| install 阶段磁盘爆 | runner 磁盘占用 | `PRUNE_BEFORE_INSTALL=1`（默认开）；确认 `prune-target.sh --before-install` 有执行 |
| 缓存命中了却仍完整重编 | 缓存 tar 里缺 `.build-done` | 复用判据是 `[ -f .build-done ] && [ -d target ] && [ -f target/package.json ]`；重打 tar 含该标记 |
| 上传 artifact 报堆溢出 | 745M+ 海量小文件逐文件压缩 | 先 `tar -czf` 上传单文件（`compression-level: 0`） |
| `sh: pnpm: not found` | `tools/pnpm/bin/pnpm` 垫片缺失或 PATH 未前置 | `build-common.sh` 会自动生成垫片；确认 `PATH="$PNPM_BIN_DIR:$PATH"` 生效 |
| `Unknown option: 'frozen-lockfile'` | 传了空参数导致解析错位 | 去掉空参数；`check-packaging-invariants.py` 有一条盯这个 |
| 装依赖白等 90 秒 | 参数类错误被当成网络错误重试 | 参数类错误立即中止（`Unknown option` / `ERR_PNPM_BAD_OPTION` / `ERR_PNPM_INVALID`） |
| 构建卡在 prune 之后十几分钟 | `glob('**')` 跟随软链导致组合爆炸 | 用 `os.scandir`（不进 node_modules、不跟随软链）；`check-packaging-invariants.py` 拦该写法 |
| 历史包名残留挂在 Release 上 | 产物改名后旧名不替换 | `python3 scripts/prune-release-assets.py --tag <tag> --keep-from <dir>` 先 `--dry-run` 再看要删什么 |
| 后台在偷偷派发构建 | `ps -ef \| grep -c '[b]ackfill-all'` 应为 0 | 有野生调度器先停手；派发脚本必须登记 pid + 日志、可一键停 |
| 构建失败但日志被截断 | 只看 tail 20 行 | 看完整日志 artifact（`build-target-debug-log` / `pack-and-release-debug-log`），失败打尾 80 行 |

## 7. 运行环境

### 7.1 侧边栏终端不可用

报错 `subprocess-local: command "/sbin/nologin" is not an executable file`：NAS 把服务账号登录 shell 记成 `/sbin/nologin`，但系统里没有这个文件。

```bash
scripts/fix-login-shell.sh --check          # 只读探测（精简输出）
scripts/fix-login-shell.sh                  # 只读探测报告
scripts/fix-login-shell.sh --patch          # 幂等插入兜底（默认自动定位 start.sh）
scripts/fix-login-shell.sh --passwd         # 改 /etc/passwd（需 root + 输入确认串）
```

运行时兜底（`start.sh` 已内置）：`[ -x "${SHELL:-}" ] || export SHELL=/bin/bash`。判据只认**已导出**的 `SHELL`——bash 在未设时会自填一个非导出的 `$SHELL`，node 子进程看不到，按 shell 变量判会误报。修补只改运行时环境，不给服务账号可交互登录 shell。

### 7.2 插件装完不生效

见 §1.3（DSH_HOME 不一致）。装完必须重启服务才加载：`synopkg restart <app>` / `appcenter-cli stop && start`。

### 7.3 CPU 占用高、系统卡顿

```bash
scripts/set-dsh-cpu-quota.sh ; scripts/verify-dsh-cpu-quota.sh
```

### 7.4 会话在新版本里看不到

```bash
scripts/migrate-session.sh --list                       # 看有哪些会话
scripts/migrate-session.sh --check <session.jsonl.zstd> # 校验格式契约
scripts/migrate-session.sh --fix-layout                 # 修 sessions/ 根下裸目录
scripts/migrate-session.sh --cwd <新cwd> --in <源> --id <会话id>
scripts/migrate-session.sh --rollback [备份名]
```

两类格式契约：`sessions/` 根下出现裸目录会让激活失败（工作区列表为空）；`session.jsonl.zstd` 的首帧必须恰好是一行 header，整体重压缩会把帧合并成一帧导致读不出。

## 9. 排查纪律

1. **先验证再下结论**：任何判断都要有一条能复现的命令与输出，没证据的写成待验证。
2. **相关不等于因果**：观察到「有 A 就好、没 A 就坏」时，先控制其它变量（包括「重启」这个动作本身）做两向对照，再找机制（配置项 / 日志 / 平台二进制字符串），不要据此定必需项。
3. **权威来源优先级**：平台官方文档 → 平台二进制里的字符串 → 平台自己的日志 → 平台配置 → 真机两向对照 → 跨应用推断（最低，且必须标注为推断）。
4. **一次只改一个假设**：改完立刻用同一组判据复测；连续多轮无进展时，先怀疑测量本身是否被污染。
5. **别用刷新当结论**：刷新只能作为验证手段，问题现象存在就说明有原因要查。
6. **修完固化**：每个新根因都要落进本文对应小节，并尽量做成守卫（`scripts/check-*.py`），让它改坏就红。
