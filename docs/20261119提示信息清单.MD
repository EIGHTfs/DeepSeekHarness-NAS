## 〇、先看这条：升级时提示「已卸载」

```
现象：手动升级到新版本，界面上弹出「已卸载」
触发链：套件生命周期 preuninst → installer 的 preuninst() 以 DSH_UNINSTALLING=1 调 start-stop-status stop
        → start.sh 的 cmd_stop 检测到该变量，把原本的「DSH 未运行」改说成「已卸载」
根因：群晖升级流程会调用 preuninst（旧版本被卸载），但 preuninst 未区分「升级」与「真卸载」
影响：升级场景下措辞与事实不符，观感像「装失败 / 被卸载」
```

两处相关代码位置（仅供参考，勿直接改）：

```
- 提示输出：build/start.sh.example → cmd_stop 的「未运行」分支
- 置标记处：build/SPK/pack-spk.sh 的 preuninst()；已安装包的 scripts/installer 同款一行
```

## 三、建议优先裁决

| 位置 | 现在的样子 | 问题 |
|---|---|---|
| start.sh · cmd_stop「未运行」分支 | `已卸载` | 升级时也会走到这里，与事实不符 |
| start.sh · cmd_stop「未运行」分支 | `DSH 未运行` | 与上一条同分支，两条措辞要一起定 |
| start-stop-status · start() | `启动仍在进行中（端口 N 尚未监听），交由系统 status 判定` | 用户看不懂「status 判定」，正常现象写得像告警 |
| start-stop-status · 端口缺失 | `错误：未找到 <路径>（端口应由打包时生成），无法确定服务端口` | 暴露内部打包细节，用户无从处理 |
| installer · 卸载保留数据 | `[uninstall] 保留数据（wizard_delete_data=…）: <路径>` | 前缀与参数名直出，像调试输出 |

- 只登记 `echo` / `printf` 直接输出、且是给人看的文本；函数返回值与机器协议输出单列。
