# Skill：运行与门户（start.sh）

> 本文件承载 `start.sh` 与三端口的解释性内容。README 只给命令与端口表。

## 1. 服务生命周期

`start.sh {start|stop|restart|status}`。启动流程：解析实例目录 → 生成/读取端口 → 拉起 DSH（`dsh web`）→ 等待就绪 → 启动反代 → 从日志提取 token → 同步门户配置。

## 2. 实例定位（多布局自适应）

脚本按候选顺序探测实例根目录（`$DSH_HOME`、包内 `target/`、`@appdata` 下的用户目录等），并把结果写入名牌与门户。多布局共存时以"实际存在 `package.json` 的那一层"为准。

## 3. 品牌与版本名牌

网页左上角显示 `brand_name + 版本号`。取值链：`build-config.yaml` 的 `defaults` → 平台段覆盖（`spk:` / `fpk:`）；版本号优先级链由 `brand_version_order` 控制（`dsh` → `npm`），**不允许自定义**（永远同步官方源码 `package.json` 的 `version`）。

## 4. 反代：门户免密 + 局域网硬闸 + 直连 403

判定顺序（**改判定时必须同步 README 的门户章节**）：

```
⓪ 局域网硬闸      → 非局域网来源一律拒绝
① URL 自带 token  → 直接放行（门户入口正是这种）
② 已持 dsh-auth cookie → 放行（token 换 cookie 后 30 天内免密）
③ 门户打开        → 302 到带 token 的 URL
④ 地址栏直连      → 403 提示"请从套件图标打开"
```

**为什么门户 URL 无条件携带 token（2026-10-07 方案 A）**：早期用 `Sec-Fetch-Site` 区分"门户打开"与"地址栏直连"，但浏览器新开标签页（DSM 打开套件的方式）与地址栏手输**同为 `none`**，无法区分 → 门户打开被误判为直连而 403。现改为让门户入口 URL 自带当前 token，完全不依赖该请求头。

**token 轮换**：token 每次 DSH 启动都会变，故 `start.sh` 启动成功后调用 `sync_portal_token()` 把当次 token 写入门户配置的 `url` 字段；服务已在运行时也同步一次（无需重启即可刷新）。

**与安装期重写的兼容**：`pack-spk.sh` 的 `apply_wizard_ports()` 在安装期只改 `port` 字段（`sed` 精确匹配 `"port"`），不会冲掉运行期写入的 `url` 字段。

## 5. 容器页面（第三个端口）

除反代端口与 DSH 原生端口外，另有一个容器页端口（默认 3082），用于在同一套件内提供独立入口。

## 6. DSH_HOME 与插件安装

`start.sh` 在服务侧 export `DSH_HOME`，并提供 `dsh` 命令 wrapper，使插件安装落在正确 home（历史上曾落到错误目录）。

## 7. 登录 shell 兜底

侧边栏终端依赖登录 shell 环境；脚本在必要时补齐 PATH（含随包 node/pnpm 目录），保证终端可用。

## 8. 三端口一览

| 端口 | 用途 | 默认（SPK / FPK） |
|---|---|---|
| 反代端口 | 门户入口；token 认证 + 免密 cookie | 30800 / 3080 |
| DSH 原生端口 | DSH 自身监听 | 30801 / 3081 |
| 容器页端口 | 独立容器入口 | 30802 / 3082 |

端口权威在 `build/build-config.yaml`（`defaults` / `spk` / `fpk` 三段，**段名必须是映射** —— 读取方按 `sec.get('proxy_port')` 取值；写成标量会静默读不到端口段，守卫 `check-build-config.py` 会拦）。脚本与网页代码中禁止出现端口字面量，需要时调 `read_ports <system>`。

## ★ DSM：装完「只瞬间能访问、页面加载不完」→ 每个响应 400（2026-10-10 真机）

**症状**：群晖 DSM 7.4.1 装好后，门户**偶尔能连上一瞬**、页面永远加载不完；
`appcenter/synopkg` 侧显示 running，端口有时齐有时不齐（`ss` 为 0/3）。

**定位过程（可复用的套路）**：
1. 反代日志显示"换 token→303 ✅，带 cookie 取 `/` → **400 空 body**"；直连 DSH 端口同样 400 ⇒ 与反代无关；
2. 规律：**只要文件存在就 400**（`/`、`/index.html`、`/assets/*`、`/manifest.webmanifest`），
   不存在的路径给 404，`HEAD /` 给 401，`POST /` 给 405 ⇒ 是**处理器抛异常被统一转 400**；
3. 排除了：包损坏/权限/TMPDIR/`.dsh` 状态/`--trusted-host` 信任栅栏（全部实测排除）；
4. **决定性一招**：给 web 载体的兜底 catch 临时插一行 `console.error(err.stack)`，
   再触发一次 400 → 拿到真实异常：
   ```
   TypeError: invalid media type
     at content-type.parse
     at negotiator@1.1.0/lib/accept.js:29 parseAccept      ← 用媒体类型解析器解析"编码"
     at negotiator@1.1.0/lib/encoding.js preferredEncodings
     at compression@1.8.2 onResponseHeaders（钩住 res.writeHead）
     at serveStatic (@deepseek-ai/dsh-host-frontend-static/lib/index.js:73)
   ```

**真因（依赖链接层，两个缺陷叠加）**：
- `compression@1.8.2` 声明 `negotiator "~0.6.4"`，载荷里也**有** `negotiator@0.6.4` 实体；
- 但 `compression` 的**包内** `node_modules/negotiator` 缺失（Node **不看兄弟位**），
  而修复脚本的"包内"那一步只在 `.pnpm` 扁平枚举里用 **`pick_entity`（无脑取最高版本）**；
- → Node 向上走到**提升层**的 `negotiator@1.1.0`（Express 5 那份）；
- → `negotiator@1.1` 在 encoding 路径上用 `content-type.parse('gzip')` → **TypeError**；
- → 异常抛在 `res.writeHead(200,…)` 内 → 载体 `handle().catch` → **每个响应都 400 空 body**；
  随后 `dsh: fatal uncaught exception` → `[!] DSH 退出 code=1` → 崩溃重启循环。

**修法（三层，缺一不可）**：
1. **运行期自愈**（`build/start.sh.example` 内嵌 JS）：新增 `satisfies()` 与
   `pickEnt(name, range)`（取**满足声明范围的最高版本**），新增 `fixPnpmPkgs()` 遍历
   `.pnpm/<pkg>@<ver>/node_modules/<包>/`，按该包 `dependencies/optionalDependencies/peerDependencies`
   的声明范围**补齐并纠正**包内链接；汇总行增加 `.pnpm 包内 N 条`。
2. **构建期**（`build/fix-node-links.py`）：同款 `satisfies()` / `pick_for_range()`，
   并把包内那一步由 `link()` 改为 `relink()`（纠正错链，不只补缺）。
3. **守卫**：不变量 [23]（构建期与运行期都按声明范围选版本），反向验证必须让
   被检查的子串**消失**（加后缀不算 —— 我第一版就因此得到假绿 ✗）。

**真机验证**：全量同步后修正 **81 条**包内链接 → 连续 3 轮 `/`、`/assets/*` 均 **200**（间隔 8 秒），
进程稳定、不再出现退出行 → 用户确认修复成功。

**通用教训**：`"多版本一律取最高"` 是错的 —— 第三方包必须按**消费者声明的 semver 范围**选版本；
且**包内链接**（第三层）必须真的建在**包自己**的 `node_modules` 里，兄弟位与提升层都可能被误命中。
