# Skill：通用开发规范（从真实事故提炼）

> **适用范围**：本仓库（DSH NAS 打包工程），以及任何"人/AI 混合编辑 + 真机验收"的工程。
> **每一条都对应 2026-10-09 ~ 10 的真实事故**（FPK/SPK 打包与飞牛真机验收现场），
> 不是一般性说教。每条包含：【事故】【规范】【强制手段】【验收】。
> 与 `docs/skills/飞牛FPK打包与排障.md`（FPK 专项）配套：本文讲"怎么不出错"，那篇讲"FPK 怎么排障"。

## 0. 总纲（一句话）

**"手工执行能成、写成脚本就错"的根因，几乎总是"凭记忆重新组织"，而不是"照抄已验证的命令"。**
故一切固化的第一原则是：**只包装已被验证过的命令**；一旦开始"重新组织"，就必须当成高风险动作，
用断言 + diff 复核 + 反向验证三重保险。

---

## 1. 提交门禁（硬性，缺一不可）

任何提交前必须全部满足，任一不满足**一律不提交**：

| # | 门禁 | 命令 / 手段 |
|---|---|---|
| 1 | 语法检查通过 | `bash -n` / `python3 -m py_compile` / `node --check` / YAML 结构守卫 |
| 2 | 全部守卫通过 | `scripts/check-*.py` 逐个跑（当前 8 个） |
| 3 | **自己的实测脚本退出码 = 0** | 写成退出码，纳入门禁 |
| 4 | diff 复核：确认没有整段删除 | `git diff` 逐条看；关键内容抽查 |
| 5 | 只 add 自己改的文件 | **绝不 `git add -A`** |

> **事故 A（门禁漏了自己）**：本地实测已报 `NameError: name 'nm' is not defined`，
> 但门禁只查了"八守卫"，于是我把它提交了 → 下一次构建才暴露。
> **规范**：自测必须写成退出码，且与守卫**同级**纳入门禁。

## 2. 编辑安全规范

### 2.1 禁止"字符串锚点 + 静默兜底"做替换或删除

> **事故 B（最严重）**：用"回退插入步骤"的脚本，以 `s.find('\n      - name: ')`（6 空格）找边界，
> 而后续步骤是 4 空格 → 找不到 → 走了 `block = s[i:]` 兜底分支 → **把插入点之后的 62 行全删了**
> （含 `上传 target`）→ `build-target` 成功但没上传 artifact → 打包 job 失败。

- **规范**：所有破坏性编辑必须 `assert 命中次数 == 期望值`，**命中数不符立即中止**；
  优先按**行号或结构**定位；兜底分支一律改为"报错退出"，不得"猜一个范围"。
- **强制**：编辑脚本内联断言；关键文件（`action.yml`、`pack-*.sh`、守卫）改动后必须 `diff` 复核。

### 2.2 注释必须独占一行

> **事故 C**：在 Python 字典构造行中间插入 `# 注释`，把该行后半段（`"links": …`）注释掉，
> 直接 `KeyError: 'dangling'`。

- **规范**：任何语言的**行内注释**只允许出现在"该行本身就是独立语句"时；
  多语句/多行结构（dict、list、JS 对象、YAML flow）**禁止**行内注释。

### 2.3 抽取代码块必须按结构边界

> **事故 D**：需要把 `start.sh` 内嵌的 JS 函数抽出来单独跑，用"找下一个 `function `"作结束边界；
> 而该函数后面已无 `function` → `find` 返回 -1 → **抽出后面整段 shell（53KB）** → `SyntaxError`。

- **规范**：抽取用**括号/引号配平**或 **heredoc 结束符**（`<<'EOF'` … `EOF`）为边界；
  抽出后必须 `assert` 长度区间 + 语法可编译（`node --check` / `bash -n` / `py_compile`）。

### 2.4 YAML / action 的缩进是硬约束

> **事故 E**：给 `action.yml` 插步骤时用了 6 空格（同级是 4 空格）→ GitHub **拒绝加载整个 action**
> → 构建在 0 秒失败，连续 3 次（#99/#101/#102）。

- **规范**：改 action/ workflow 后，必须校验**同级 `- name:` 缩进一致**（守卫 `check-workflow-yaml.py`
  新增 `check_step_indent`）；改动后先在本地跑 YAML 结构守卫。

### 2.5.1 断言 / 计数必须精确到能覆盖真实写法

> **事故 K（本轮新增）**：给文档加可折叠块后，我用 `grep -c '<details>'` 统计配平，
> 结果报「1 / 2 不配平」—— 而真实状态是正确的：第二个块写的是 **`<details open>`**，
> 不含 `'>'` 紧邻，自然匹配不到。**是检查写错了，不是文件坏了。**

- **规范**：做断言/计数前，先确认**目标字符串的所有真实写法**（`<details>` / `<details open>`
  / `key = value` / `key=value`）；计数类断言要匹配"前缀"而不是"完整片段"；
  最好再用**解析器**复核一次（如折叠块：递归计深度、要求每块紧跟 `<summary>`、收尾深度为 0）。
- **推论**：凡"我的检查说坏了"，先怀疑检查 ✗ —— 与 3.3（对照物 0 告警）同源。
- **再加一条**：凡是"在文档里**举例说明**某标签/语法"的文本，都会被**朴素的计数器**误当成真标签。
  例如本文这段就写着折叠标签的两种写法 → 统计时必须**行首锚定**（`^\s*<details\b`）
  并**排除代码 span / 反引号内**的示例。**这条坑当天就现报现踩**（写规范的同时把规范自己的
  计数器弄坏了 ✗）—— 所以：检查器要按"真实语法位置"匹配，而不是全文 `count()`。

### 2.5 语法检查 ≠ 完整性检查

> **事故 B 的放大器**：`bash -n`、AST、`py_compile` 全部通过，但文件已少了 62 行。

- **规范**：任何"整段删除"类风险，只能靠 **diff 复核 + 关键内容抽查**（如 grep 关键步骤名、
  行数/步骤数与历史比对）发现。

## 3. 守卫（Guard）规范

### 3.1 每条守卫必须"反向验证"

- **规范**：新增/修改守卫后，**故意破坏对应代码** → 守卫必须失败（退出码非 0）；
  **还原** → 守卫必须通过。两次都要记录在提交信息里。
- **为什么**：本轮就出现过"守卫看着绿、其实无效"——见 3.2。

### 3.2 内容检查必须先剥注释（防"假绿"）

> **事故 F**：我写了"必须存在 `cp -a "$APP_DIR/ui/."`"的守卫；而我在固化时把命令原文写进了**注释**。
> 反向验证：**删掉真代码、保留注释 → 守卫仍然通过**（假绿）。

- **规范**：所有"文件中必须存在 X"的检查，先剔除注释行（`#` / `//`）再匹配；
  既查"存在"也要防止"仅注释里存在"。

### 3.3 新检查器必须先在"已知合格的对照物"上跑通

> **事故 G**：为对比"手工成功包 vs 自动构建包"，我写了悬空软链判定；
> 反向自检：把**官方 2.0 基准包**当候选 → 报 **5638 条悬空**，而它真机安装运行正常。
> 根因是工具两处 bug：tar 目录条目带结尾斜杠、清单路径带 `./` 前缀 → 精确匹配失败。

- **规范**：任何"报警器"上线前，必须在**已知合格的参照物**上跑出 **0 告警**；
  参照物报警 → 先修检查器，不许结论"包有问题"。这条正是"改之前先找能打开的对照物"的镜像用法：
  **对照物不仅用来验代码，也用来验工具**。

### 3.4 守卫要能在构建之前一键失败

- **规范**：守卫登记进 CI 的"守卫套件"步骤（秒级），保证坏包**烧不到构建**；
  出货级验包（`check-fpk-payload.py`）在打包后跑。

## 4. 诊断规范

### 4.1 权威来源优先于推断（并列优先级）

1. 官方文档：`docs/官方文档/fpk/**`、`docs/官方文档/spk/**`
2. 平台二进制的字符串：`strings /usr/trim/bin/trim_app_center | grep -i …`
3. 平台自己的日志：`/var/log/trim_app_center/{error,info}.log` ★
4. 平台配置：`/usr/trim/nginx/conf/conf.d/*.conf`、`config/privilege`
5. 真机实测（两向对照）
6. 跨应用推断 ← **最低，且必须标注为推断**

### 4.2 相关 ≠ 因果：两向对照必须控制变量

> **事故 H（反复十余次的根源）**：观察到"有 `/var/apps/<app>/ui/config` 时按钮可用、
> 删掉就消失"，据此认定它是必需项，反复手工补；**真因**其实是 fnOS 应用中心判定
> **启动失败（error 10330）**，而 10330 由两处生成物 bug 引起（下节）。
> 更早还据"1Panel 的 `/var/apps` 下没有 ui/"推断不需要 —— 同一个坑的两个方向。

- **规范**：两向对照必须**固定其它变量**（含"重启"这个动作本身），并尽量用**权威产物**给出机制；
  仅凭"有 A 就好 / 没 A 就坏"不得写成因果结论。

### 4.3 结论必须标注证据类型

- **规范**：写"实测（命令 + 输出）"或"推断（无证据）"。推断**不得**以结论语气出现；
  本轮至少有 4 次把推断当结论（ui 必需、目录条目必需、icon 命名、权限）。

### 4.4 先读原文，再改

- **规范**：改任何文件前先 `read` 它的真实结构（或 `sed -n` 打印带行号的原文）；
  禁止凭记忆写锚点/缩进/字段名。本轮因"凭记忆"导致的锚点未命中至少 6 次。

## 5. 后台任务与外部状态

### 5.1 会改变外部状态的脚本必须登记、可控、可杀

> **事故 I**：早前写的 `backfill-all.sh`（历史版本补全调度器）在后台**持续派发构建**；
> 我据此把 #104/#106/#108 误判为"我派的构建"，还反复困惑于"构建为何自己开始"。
> 更糟的是我用 `pgrep` 校验"是否还在跑"，而它匹配不到 → 我以为已停止。

- **规范**：
  - 派发构建/发布/部署的脚本，运行时必须登记（pid 文件 + 日志），并能一键停止；
  - 校验进程用 **`ps -ef | grep`（配合字符类避免自匹配）**，不要只信 `pgrep`；
  - **动手派发前先确认零野生调度器**：`ps -ef | grep -c '[b]ackfill-all'` 应为 0。
  - 派发后立刻记录 run 号 + head sha，避免"构建归属误判"。

### 5.2 构建是稀缺资源

- **规范**：一次修复一次构建；能本地验证的绝不烧构建；
  并发策略会取消旧 run，故"发新票"等价于"丢弃旧票"，发送前要说明；
  **未经用户同意不得派发历史版本补全**。

## 6. 固化协议（用户给定，强制）

**核心**：只包装**已经验证过**的命令；禁止凭记忆重新组织。

写脚本时**只做四件事**：
1. 加 shebang（`#!/usr/bin/env bash`）
2. 加严格模式（`set -euo pipefail`）
3. 加显式检查（cwd / 用户身份 / 依赖是否存在）
4. 加变量（默认值 = 手动执行时的实际值）

**禁止**：重新组织命令、省略"看起来冗余"的步骤、把多条命令合并、改变参数顺序。

**验证**：
- 换环境重跑（换目录 / 换身份）；
- **逐步比较中间产物**（步骤 1/2/3 各自比），不只比最终产物；
- 不一致就说明有隐式差异（cwd / 环境变量 / 用户 / shell 类型 / 隐式判断 / 顺序 / 通配符 / 错误中止）。

```bash

  python3 scripts/$g.py >/dev/null 2>&1 && echo "$g ✓" || echo "$g ✗ 阻断提交"; done

# ② diff 复核：确认没有整段删除

# ③ 反向验证（新增/修改守卫时）
<故意破坏>  → 守卫必须非 0

<证据：实测命令与输出>
<修法>
<验证：反向验证 + 守卫清单>
```

## 9. 一页话总结

1. **只包装验证过的命令**，禁止凭记忆重组。
2. **破坏性编辑必须有断言**，改完必须 diff。
3. **守卫必须反向验证**；内容检查先剥注释。
4. **新检查器先在合格对照物上跑出 0 告警**。
5. **权威来源优先**（官方文档 / 二进制字符串 / 平台日志 / 实测），推断必须标注。
6. **相关不等于因果**，两向对照要控制变量。
7. **自测失败或守卫失败 → 一律不提交**。
8. **不空等、不猜、不烧构建**；每轮产出"诊断 + 修复 + 反向验证 + 提交"闭环。
