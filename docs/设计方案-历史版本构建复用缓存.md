# 设计方案：历史版本构建复用缓存（两层缓存 + 分层失效）

> 起因：补全 26 个历史版本时，每个版本都要跑一次完整构建（install + build + 裁剪 + 打包，
> 约 15-20 分钟）→ 合计约 **8 小时** ✗。而其中**最贵的那段（install + build，约 15 分钟）
> 其实与打包脚本无关**。本文给出可落地的两层缓存方案，并给出**不重新打包即可验证**的路径。

## 一、现状与根因

### 1.1 一次构建的三段时间成本

| 阶段 | 做什么 | 耗时 | 依赖什么 |
|---|---|---|---|
| **A 构建** | 复制官方源码 → `pnpm install` → `pnpm build` | **~15 分钟** | 官方 tag + 构建工具链 |
| **B 裁剪** | `prune-target.sh` 纯白名单删 `.pnpm` + 源码/文档 | ~1 分钟 | 白名单 + 裁剪脚本 |
| **C 打包** | 后处理 + 打 SPK/FPK + 发布 | ~2 分钟 | 打包脚本 + 配置 |

### 1.2 根因：缓存键把 B/C 的脚本也算了进去

`.github/actions/build-target/action.yml` 现在这样算 target 缓存键：

```
key: dsh-target-v2-<tag>-<hashFiles(
       build/build-config.yaml, build/build-common.sh, build/prune-target.sh,
       build/prune_common.py, build/build-prune-whitelist.json,
       scripts/lib/common.sh,
       .github/actions/build-target/action.yml, .github/actions/pack-with-target/action.yml)>
```

问题在于：
- 里面**混入了 B/C 的输入**（白名单、裁剪脚本、打包 action）→ 这些一改，**所有历史 tag 的
  target 全部失效** ✗ —— 这正是本次"修完 bug 后补历史版本要 8 小时"的直接原因。
- 而 A 段（最贵的 15 分钟）**只依赖官方 tag + 工具链**，与 B/C 无关 ✗ → 白白重跑。

### 1.3 另一个隐含问题

现在缓存的是**已裁剪**的 target。而裁剪**依赖白名单** → 白名单一变，缓存内容就"语义过期"，
所以不得不把白名单塞进 key。**把缓存内容从"已裁剪"改成"未裁剪"，这个耦合就消失了。**

## 二、方案：两层缓存 + 分层失效

### 2.1 分层

```
                 ┌──────────────────────────────────────────────┐
官方 tag ───────▶│ L1 构建产物缓存（未裁剪 build 输出）          │  键只含 A 段输入
                 │   key = v1-build-<tag>-<hash(A 段输入)>       │  命中 → 跳过 ~15 分钟
                 └───────────────────────┬──────────────────────┘
                                         │ 解包即得 source/(含完整 node_modules) + 源码
                                         ▼
                 ┌──────────────────────────────────────────────┐
                 │ L2 裁剪 + 打包（**不缓存**，每次跑）          │  ~3 分钟
                 │   prune-target.sh → fix-runtime-deps.sh      │  白名单/打包脚本改了
                 │   → pack-spk.sh / pack-fpk.sh                │  **不需要重建 A**
                 └──────────────────────────────────────────────┘
```

### 2.2 缓存键怎么切

| 键 | 包含 | 不包含（关键） |
|---|---|---|
| **L1 构建产物** | 官方 tag、`node`/`pnpm` 版本、`build-common.sh` 的 **install+build 段**（可拆成 `build/build-stage.sh`）、随包运行时（`tools/`） | **白名单**、**prune-target.sh**、**prune_common.py**、**pack-spk.sh**、**pack-fpk.sh**、**build-config.yaml** 的打包段 |
| L2 | 不缓存（每次跑） | — |

要点：
1. **`build-common.sh` 拆成两半**：`build/build-stage.sh`（A 段：install + build，产出未裁剪的
   `source/`）与 `build/build-common.sh`（B/C 段：裁剪 + 补包 + 写 meta）。
   这样 L1 的键可以只哈希 `build-stage.sh`，B/C 的改动不再波及缓存。
2. `build-config.yaml` 里**端口/品牌/版本**属打包段（B/C），不应进 L1 键；
   若嫌拆分麻烦，可先把它整体留在 L1 键里（它极少改）。
3. **缓存内容改为"未裁剪"**：体积更大（实测未裁剪 `source/node_modules` ≈ 6.6G），
   但换来"白名单随便改都不用重建"。压缩上传前用 `tar -cf`（单文件，避免 upload-artifact 逐文件 OOM）。

### 2.3 缓存放在哪：GitHub Actions 缓存 + NAS 本地长期基线

GitHub Actions 缓存有 **7 天未访问即回收**的限制 ✗ → 历史 tag 的缓存放久了会没 ✗。
因此建议**双存放**：

| 存放 | 用途 | 生命周期 |
|---|---|---|
| Actions cache（`actions/cache@v4`） | 同一 tag 的快速复用（近 7 天内） | 7 天 |
| **NAS 本地缓存目录**（本机 407G 可用） | **长期基线**：每个 tag 一份 `build-<tag>.tar.zst` | 永久（人工清理） |
| Release 资产（可选） | 极端情况下的异地备份 | 永久 |

本地缓存的取用方式：CI 里先尝试 Actions cache，未命中则从 NAS 拉（内网 SMB/HTTP），
构建完成后回写 NAS。**这样即使 Actions 缓存被回收，也不需要重新跑 A 段。**

## 三、"不重新打包就能验证"的路径（用户核心诉求）

方案落地后，验证一个打包改动只需 **B/C 段（约 3 分钟）**，且**不必产出正式包**：

### 3.1 已有能力可直接用

```bash
# 只跑 A 段（已有 SKIP_BUILD / BUILD_STAGE 机制）
BUILD_STAGE=install ./build/build-common.sh     # 复制源码 + pnpm install
BUILD_STAGE=build   ./build/build-common.sh     # 只 build

# 只跑 B 段（裁剪 + 补包）—— 已有 prune 阶段
BUILD_STAGE=prune   ./build/build-common.sh     # 对已有 target 重新裁剪 + 补包
```

### 3.2 新增一个"只验证不出包"的入口（建议）

```bash
./scripts/verify-packaging.sh [--tag <tag>] [--no-pack]
#   1) 确保 L1 缓存就绪（命中即解包；未命中才跑 A 段）
#   2) 跑 B 段：prune-target.sh + fix-runtime-deps.sh
#   3) 跑守卫：
#        scripts/check-packaging-invariants.py        （12 项打包不变量）
#        scripts/check-package-parity.py <基准包> <新包>  （结构/软链/悬空目标比对）
#   4) --no-pack 时【不生成 spk/fpk】，只对 target 做静态判定并打印结论
```

**`--no-pack` 的判定口径**（不产出安装包也能定论）：
- target 内 `.pnpm` 目录数 ≥ 基准包内数量；
- `links.tar` 的每个目标在 target 内存在（复用 `check-package-parity.py` 的悬空检测逻辑，
  把"载荷条目集"换成"target 文件集"）；
- 打包不变量 12 项全绿。

### 3.3 端到端验证（真要装的话）

```bash
# 只在最后一步才出包；出包后按 skill 文档第八节验收：
#   status=running + 三端口 + 日志无 failed to import + 套件图标模拟 200
```

## 四、成本对比（26 个历史版本）

| | 现在 | 方案落地后（L1 全命中） |
|---|---|---|
| 每版本 | A 15min + B 1min + C 2min ≈ **18 分钟** | B 1min + C 2min ≈ **3 分钟** |
| 26 个版本 | ≈ **8 小时** | ≈ **1.3 小时** |
| 之后改白名单/打包脚本 | **全部失效，重来 8 小时** ✗ | **L1 仍命中**，只重跑 B/C ✓ |

## 五、落地步骤（可增量，每步都能单独验证）

1. **拆脚本**：把 `build-common.sh` 的 A 段抽成 `build/build-stage.sh`（行为不变，
   `build-common.sh` 继续可用）→ 跑一次本地构建确认产物一致。
2. **改缓存键**：L1 键 = `v1-build-<tag>-<hash(build-stage.sh, tools/, node/pnpm 版本)>`；
   缓存路径指向**未裁剪**的 `source/`（含 node_modules）。
3. **L2 保持每次跑**：`build-common.sh` 从 L1 解包后执行 prune + fix-runtime-deps + meta + 打包。
4. **加 NAS 长期基线**：构建完成后 `tar --zstd` 回写 NAS；CI 未命中 Actions cache 时先查 NAS。
5. **加 `scripts/verify-packaging.sh`**（含 `--no-pack`）。
6. **更新守卫**：`check-packaging-invariants.py` 增加两项——
   「L1 缓存键不得包含白名单/打包脚本」「存在 verify-packaging.sh 入口」。

## 六、风险与取舍

| 风险 | 说明 | 对策 |
|---|---|---|
| 未裁剪缓存体积大 | `source/node_modules` ≈ 6.6G（压缩后仍数 GB） | 放 NAS 为主、Actions cache 为辅；只在需要时拉 |
| 缓存与真实源码不一致 | 若 tag 内容被上游改写（极少） | L1 键含 tag + 源码镜像的 commit sha |
| 拆脚本引入回归 | `build-common.sh` 是核心 | 拆完先做"新旧产物逐字节比对"再切换 |
| Actions 缓存 7 天回收 | 历史 tag 复用率低 | NAS 长期基线兜底 |

## 七、与"要不要补历史版本"的关系

本方案**不改变**"是否补历史版本"这个决策 —— 它只是把"补"的代价从 8 小时降到 1.3 小时，
并让**后续任何打包改动都不再需要重跑构建**。是否补、补哪些，仍由用户决定；
待补清单在 `/tmp/backfill-tags.txt`（26 个，未执行完，已按要求暂停）。
